# 개발 공정 (정본)

> 이 프로젝트를 어떤 순서로, 어떤 규칙으로, 어떤 세션 구성으로 개발하는지 정한다. 공정관리 세션이 관리한다.
> 관련: [문서 정본 지도](README.md) · [현황판](STATUS.md) · [결정 로그](DECISIONS.md) · [뼈대 설계](design/skeleton.md) · [PRD](PRD.md)
> 수립: 2026-11-06 (오너 결정: `main`을 기준 브랜치로 · PR #7 먼저 머지 · 문서 정본 수립 · 구조를 먼저 정하고 튜닝은 뼈대 완성 뒤에 · 공정관리 세션과 개발 세션 분리)

## 0. 요약

1. **기준은 하나:** 코드와 문서 모두 `main` 브랜치가 정본이다. 작업 브랜치의 변경은 머지 전까지 초안이다
2. **순서는 뼈대 → 파트 → 튜닝:** 구조 결정을 빠르게 끝내 모든 시스템의 자리를 만들고(S), 그 안을 파트별로 병렬로 채우고(P), 마지막에 밸런스를 한 번에 잡는다(T). 그다음 Godot 이식(G)·비주얼(V)
3. **번호는 머지할 때 발급:** 작업 브랜치는 임시 ID를 쓰고, `main`에 머지할 때 공정관리 세션이 결정 번호·PRD 절 번호를 매긴다. 병렬 세션끼리 번호가 겹치지 않는다
4. **세션은 역할로 나눈다:** 공정관리 1개(상시) + 단계별 작업 세션. 뼈대 단계는 설계 세션 1개, 파트 단계는 파트 세션 최대 3개, 튜닝 단계는 밸런스 세션 1개 (§7)

## 1. 원칙

| # | 원칙 | 이유 |
|---|---|---|
| 1 | **정본 = `main`.** 설계·규칙·결정은 `main`에 머지된 것만 유효하다 | 브랜치마다 PRD 버전이 달라지고 결정 번호가 겹치는 문제(#96·#100~#104가 두 뜻)를 막는다 |
| 2 | **구조 먼저, 튜닝은 나중** | 시스템이 더 들어오면 지금 맞춘 수치는 다시 맞춰야 한다. 결정 #77~#126의 상당수가 튜닝·밸런스 실험이었다 |

README 기준선 갱신 |
| **게이트 L 후반 경험** (#274) | 단계 T 뒤·G 전 필수 게이트 — 8~15년 구간의 의미 있는 선택·해금 시스템 활용·자동 진행과 개입의 균형·기회비용 이해·장기 숙성 판단의 역할을 검증한다. 단계 T 완료 조건에는 넣지 않는다 | 설계(게이트 설계 ARCH-E) + 파트 | 게이트용 규칙 변경을 회귀 검증 없이 넣기(경제 공식이 바뀌면 영향받은 T 실험을 다시 돈다) | 표본·합격 기준은 ARCH-E 제안 뒤 오너 승인 ([late-game-gate.md](design/late-game-gate.md), 작성 전) |
| **G Godot 이식** | 콘텐츠 JSON화 → C# 시뮬레이션 + 골든 테스트 → Godot 골격 ([architecture.md §9.2](design/architecture.md)) | 이식 1~2 | 규칙 변경 (TS 기준 구현이 먼저 바뀐다) | 골든 테스트 허용 오차 통과 |
| **V 비주얼·출시** | 픽셀 아트, 화면, Steam 연동, 실존 이름 법률 검토 | — | — | 출시 |

- PRD §14 로드맵의 Phase(2·3·4·5)는 **기능 범위 묶음**이다. 단계 S/P/T가 **진행 순서**다. Phase 2 기능의 자리는 S에서, 내용은 P에서 만든다
- **S·P 단계에서 허용하는 밸런스 작업은 "깨짐 방지"뿐이다:** 어떤 입지가 전 전략 파산처럼 명백히 깨지면 고친다. 기준선 판정·전략 간 균형 맞추기는 T로 미룬다
- 단계를 거꾸로 가는 것(T 중에 구조 문제 발견)은 정상이다. 그때는 결정부터 다시 받고 해당 파트로 되돌린다

## 3. 작업 단위의 수명

```
① 제안      [제안 P-<파트>-<n>] — 설계 문서나 PR 설명에. 근거·대안·리스크 포함
② 결정      오너가 승인 → [결정 P-<파트>-<n>] (번호는 아직 임시)
③ 구현      작업 브랜치에서 sim + 테스트 (+ 화면). 문서도 같은 브랜치에서 고친다
④ 검증      공통 검사(§6). 단계 T에서만 40시드 판정
⑤ 머지      공정관리 세션이 #번호·§번호 발급 → DECISIONS.md 행 추가 → main 머지 → 현황판 갱신
```

- 파트 약칭: `ARCH`(뼈대·코어) · `PROD`(생산·숙성·블렌딩) · `MKT`(시장·판매·B2B·수출) · `MGT`(재무·HR·이벤트·연구) · `META`(시나리오·업적·경쟁 AI) · `BAL`(밸런스) · `GD`(Godot) · `RES`(조사)
- 한 PR = 한 주제. 구조 결정과 그 구현은 같은 PR에 넣어도 되지만, 튜닝을 섞지 않는다

## 4. 브랜치·머지 규칙

| 항목 | 규칙 |
|---|---|
| 기준 브랜치 | `main` (2026-11-06부터, ciosryu/distillery#10). 옛 기준 브랜치 `claude/dazzling-mccarthy-40er1r`는 **동결** — 더 커밋하거나 머지하지 않는다 |
| 작업 브랜치 | 세션마다 하나(`claude/...`, 세션이 정한다). 반드시 최신 `main`에서 시작한다. 어떤 브랜치가 어떤 파트인지는 [현황판](STATUS.md)에 적는다 |
| PR | 작업 브랜치 → `main`, 처음엔 draft. 설명에 임시 ID, 바꾼 코어 파일, 검사 결과를 적는다 |
| 머지 | 공정관리 세션이 §6 검사를 확인하고 오너 승인 후 머지한다. **머지 커밋**(squash 안 함 — 커밋 기록이 결정의 근거다). **예외 (#286 → #294):** `src/`·`data/`를 바꾸지 않고 출력 11개·P8 기본 출력이 바이트 동일한 PR은 PM이 검사(typecheck·test·build·출력 비교)를 통과하면 오너 지시 없이 머지한다. `scripts/experiments/` 밖의 측정 도구를 바꾸는 PR은 ARCH 검토를 받은 경우만. 게임 코드가 바뀌거나 출력이 바뀌는 PR, `[제안]`의 채택은 지금처럼 오너 지시를 받는다 |
| 머지 후 | 다른 열린 브랜치는 `main`을 받아 충돌을 푼다. 공정관리 세션이 현황판에 "따라잡기 필요"를 표시한다 |
| 쌓인 PR | 다른 작업 브랜치를 기준으로 하는 PR(스택)은 피한다. 필요하면 기준 PR이 머지된 뒤 `main`으로 옮긴다 |
| 플레이테스트 판 동안 (#231) | 오너가 사람 플레이테스트 판을 하는 동안에는 **머지하지 않는다** — 판 시작부터 끝까지 같은 빌드. 판 도중 요청한 기능은 PR까지 만들고 판이 끝난 뒤 머지한다(대기열은 STATUS). 예외: 판을 막는 붕괴·버그 수정(머지하면 STATUS에 "몇 개월째부터 새 빌드"를 적는다). 화면 머리글과 기록 파일에 빌드가 찍힌다(#227) |

## 5. 번호 규칙 — 결정·PRD 절·미결 사항

| 대상 | 작업 브랜치에서 | 머지할 때 (공정관리 세션) |
|---|---|---|
| 결정 | `P-<파트>-<n>` (예: `P-MKT-2`) | [DECISIONS.md](DECISIONS.md) "다음 번호"부터 발급, 브랜치 안의 임시 ID를 모두 #번호로 바꾼다 |
| PRD 새 절 | 제목만 쓰고 번호 자리에 `§NEW-<파트>-<n>` | 다음 빈 절 번호 발급 |
| PRD §15.3 미결 사항 | 목록 끝에 `- [ ]`로 추가 | 다음 번호 발급 |
| 기존 번호 인용 | 그대로 (`main`에 있는 #1~#325는 확정) | — |

- **이 규칙 이전에 열린 PR**(#5·#6·#9)이 이미 쓰는 번호는, `main`과 겹치지 않으면 **예약**으로 인정해 그대로 발급한다(#97, #110~#117). 겹치는 PRD 절 번호만 머지 때 다시 매긴다 → [DECISIONS.md](DECISIONS.md) "예약"
- 작업 세션이 "아직 아무도 안 쓴 다음 번호"를 스스로 골라 쓰지 않는다. 병렬 브랜치끼리는 서로의 번호를 모른다 — 이번에 #96·#100~#104가 두 뜻으로 쓰인 원인이다
- 번호는 한 번 발급되면 바꾸지 않는다. 바꿔야 하면 "번호 재발급 이력"에 남긴다

## 7. 세션 구성

### 7.1 역할

| 세션 | 수 | 맡는 일 | 쓰는 파일 | 하지 않는 일 |
|---|---|---|---|---|
| **공정관리 (PM)** | 1, 상시 | 현황판 갱신, PR 검사 확인, 머지, 번호 발급, 따라잡기 안내, 오너 결정 대기 목록 관리, 단계 전환 판정 | `docs/PROCESS.md`·`STATUS.md`·`DECISIONS.md`·`README.md`, PRD §0·§14·§15 | 게임 코드 작성, 설계 결정 제안 |
| **설계 (ARCH)** | 1 (단계 S) | 구조 결정 백로그를 오너와 결정, 코어 스키마·틱·명령·마이그레이션 구현(스텁), 파트 경계 확정 | `docs/design/skeleton.md`·`architecture.md`, 코어 파일 (skeleton.md §3.1) | 튜닝, 콘텐츠 추가 |
| **파트 (P1~P3)** | 2~3 (단계 P) | 자기 파트 범위의 규칙·공식·콘텐츠·화면 | 자기 파트 소유 파일 + 자기 PRD 절 | 코어 파일 직접 수정, 남의 파트 파일 수정 |
| **밸런스 (BAL)** | 1 (단계 T, **새 세션** — #265) | 40시드 판정, 수치 조정, 기준선 기록 (파트가 준비한 측정을 돌려 판정한다 — 아래 §7.2) | `[튜닝]` 수치, `scripts/balance-sim.ts`, PRD 밸런스 기록 절 | 구조 변경 |
| **조사 (RES)** | 0~1 (선택) | PRD `[확인 필요]` 사실 확인 | `docs/research/` | 코드 |

### 7.2 단계별 구성

```
단계 S (완료)          단계 P (지금)                       단계 T
┌──────────┐          ┌──────────┐                    ┌──────────┐
│ PM (상시) │          │ PM (상시) │                    │ PM (상시) │
└──────────┘          └──────────┘                    └──────────┘
┌──────────┐          ┌────┐┌────┐┌────┐               ┌──────────┐
│ ARCH     │   ──▶    │ P1 ││ P2 ││ P3 │      ──▶      │ BAL      │
└──────────┘          └────┘└────┘└────┘               └──────────┘
┌──────────┐ 선택     (코어 변경은 코어 PR로 먼저, §7.3)
│ RES      │
└──────────┘
```

- **파트 분할 (단계 S 끝에서 확정 — #153):**
  - P1 `PROD` 생산·숙성·블렌딩
  - P2 `MKT` 시장·판매·B2B·수출
  - P3 `MGT` 재무·HR·이벤트·연구(테크트리)
  - `META`(시나리오·업적·경쟁 AI)는 P1~P3 중 하나가 끝나면 그 자리를 이어받는다 (WIP ≤ 3)
  - 파일 소유는 [skeleton.md](design/skeleton.md) §3
- **단계 P → T 넘어가는 조건 (#262, 오너 2026-11-10):** 사람 판을 더 하지 않는다. MVP 범위 파트 일 중 **판을 잃게 하는 함정**(플래그십 보호 #260·#261, 표기 하한 함정(PROD), #249 QoL ①②④, **증산 전망 화면 #271**)을 마치고, **시장·가치 식 v1(#281 — 수요·가격 식을 한 묶음으로 고치고 판정용 봇 P8을 한 번 재보정)**을 넣은 뒤 봇(P7 재실행으로 보호가 후보를 지키는지, 8입지 스모크·MVP 생존 실험 오류 0)과 후반 세이브 화면 점검으로 넘어간다. 편의(QoL ③·⑤ SOP)와 P-PROD-30·35는 단계 T 뒤. 플래그십 등급제(#263)는 판정 구조라 단계 T 전에 넣는다. **추가(#292):** 공통 불변식(180개월 유한성 스윕 오류 0·멱등성) · 자동 가격 3정책 실행 엔진 + 사유 기록 데이터(#291) · 봇 판정·순자산 정의 통일(TECH-02) · 변경 전 기준선 고정. 식 v1의 내용은 #290
- **단계 T의 측정과 판정 (#265, 오너 2026-11-11):** 측정은 파트가 준비하고, 판정은 BAL이 한다
  - 파트(PROD·MKT·MGT)는 자기 몫 확인 목록을 `docs/design/<파트>-stage-t.md`에 두고(항목·손잡이·판정 기준 `[제안]`), 측정 스크립트(`scripts/experiments/<파트>-*.ts`)를 단계 P 안에 준비한다. 단계 T에서도 파트는 예비 측정과 원인 분해를 할 수 있다
  - **40시드 판정·수치 조정·기준선 기록은 BAL만** 한다. BAL은 봇을 만든 쪽과 판정자를 나누려고 **새 세션**으로 둔다(오너가 세션 수를 줄이려면 MGT를 BAL로 바꿀 수 있고, 그때 판정 PR은 PROD·MKT가 검토한다)
  - **"잘 하는 봇"(#264)의 범위 (#278):** 목표 달성률 범위는 **최선 합리 전략**(4전략 + P8 합리 변형 중 최선)으로 판정하고, P8 X0(사람 재현)은 입문 보호 지표(#264 보조 조건 a)로 쓴다. "합리 변형" 목록은 BAL이 판정 전에 고정한다
  - **구조 변경이 필요하다고 진단되면 (#276):** OWNER-1~3(#273·#275) 진단에서 공식 모양 변경이 필요하면 오너가 건마다 승인해 **T 진입 전**에 처리한다 — 승인된 건은 #262 진입 조건에 더한다
  - **요구사항 문서 (#279):** 요구사항 ID `REQ-<파트>-<n>`. 파트 초안은 `<파트>-stage-t.md` 「요구사항」 절 → 확정 뒤 PRD 해당 절로 승격. 공통 템플릿·색인 `docs/design/requirements.md`, 밸런스 명세 `docs/design/balance-spec.md`, 후반 경험 게이트 `docs/design/late-game-gate.md`
  - **GAME 개선 프로그램 (#280, 오너 2026-11-11):** 핵심 재미·밸런스·완성도 개선은 [game-program.md](design/game-program.md)의 GAME-01~09로 관리한다. 안건마다 다섯 대안(그대로·수치·규칙/인터페이스·가벼운 연결·신규 시스템)을 비교하고, 모든 세션은 `[COUNTER-PROPOSAL]` 10항 형식으로 역제안할 수 있다(확정 결정과 충돌하면 명시하고 오너 승인). 분류 P0(T 필수)~P3, 작업 상태 8단계 — 문서에 적었다고 구현·검증 완료로 표시하지 않는다
  - **판정용 봇은 하나다:** 표준 규모 사람형 봇 `mvp-human.ts` P8(MGT가 만들고 PROD·MKT·ARCH가 검토)과 `mvp-survival.ts` 4전략. 파트 측정 스크립트는 이 봇 위에 손잡이만 얹는다(예: MKT `mkt-lib.ts`는 P8이 머지되면 옮긴다). 파트마다 봇이 다르면 숫자를 서로 견줄 수 없다
- 파트가 3개를 넘지 않게 하는 이유: 오너가 하루에 처리할 수 있는 결정 수가 병목이고, 코어 충돌·따라잡기 비용이 세션 수에 비례해 는다

### 7.3 파트 간 경계 — 코어 변경

- **코어 파일**(상태 타입·틱 파이프라인·엔진 계약·마이그레이션·새 게임·난수·공용 색인)은 파트 PR에서 직접 바꾸지 않는다
- 파트가 코어 변경이 필요하면 **코어 PR**을 따로 작게 만든다(새 필드·새 틱 단계·새 명령 타입만, 동작 없음). PM이 먼저 머지하고 나머지 파트에 따라잡기를 알린다
- 단계 S에서는 설계 세션이 코어를 소유하므로 이 규칙이 없다

### 7.4 세션끼리 정보가 오가는 길

| 무엇 | 어디에 | 누가 쓰나 |
|---|---|---|
| 지금 어느 단계인지, 누가 무엇을 하는지, 오너 결정 대기 목록 | [STATUS.md](STATUS.md) | PM |
| 확정된 결정 | [DECISIONS.md](DECISIONS.md) | PM (머지 때) |
| 제안·질문·검사 결과 | PR 설명 | 작업 세션 |
| 구조·파트 경계 | [skeleton.md](design/skeleton.md) | ARCH |

- PM은 세션 간 메시지로 파트 세션에 태스크를 직접 보낼 수 있다(2026-11-11~). 파트 세션은 이를 참고 자료로 다루므로, 오너가 "PM 태스크대로 진행"을 각 세션에 한 번 지시한다.
- 오너가 세션 사이의 전달자다. 작업 세션이 PR을 올리면 PM 세션에 "PR 올라왔다"고 알려 주면 된다. PM은 머지 뒤 현황판을 갱신하고, 다른 세션에 전할 말을 현황판 "따라잡기"에 적는다
- 저장소 루트 [`CLAUDE.md`](../CLAUDE.md)가 모든 세션에 자동으로 읽힌다 — 이 공정의 핵심 규칙과 첫 행동이 거기 있다

### 7.5 세션 시작 문구 (복사해서 쓴다)

**공정관리 세션**
```
너는 이 저장소의 공정관리(PM) 세션이다. docs/PROCESS.md와 docs/STATUS.md를 먼저 읽어라.
게임 코드는 쓰지 않는다. 열린 PR을 확인하고 현황판을 최신으로 만든 뒤, 오너 결정이 필요한 것을 정리해 보고해라.
```

**설계 세션 (단계 S)**
```
너는 설계(ARCH) 세션이다. docs/PROCESS.md, docs/design/skeleton.md, docs/design/architecture.md를 먼저 읽어라.
skeleton.md §4 구조 결정 백로그를 우선순위대로 하나씩 나에게 제안하고(근거·대안·리스크), 결정되면 코어에 스텁으로 구현해라.
수치 튜닝은 하지 않는다. 결정은 임시 ID(P-ARCH-n)로 적고, 번호는 머지 때 PM이 매긴다.
```

**파트 세션 (단계 P)**
```
너는 <파트 이름>(<약칭>) 파트 세션이다. docs/PROCESS.md와 docs/design/skeleton.md §3의 네 파트 범위·소유 파일을 먼저 읽어라.
네 소유 파일만 고친다. 코어 변경이 필요하면 작은 코어 PR을 따로 만든다. 결정은 P-<약칭>-n 임시 ID로 적는다.
세밀한 튜닝은 하지 않는다. PR 전에 docs/PROCESS.md §6 공통 검사를 돌려라.
```
