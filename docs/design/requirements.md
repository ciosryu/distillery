> 등급: **정본(형식)**. 요구사항 문서 체계는 `[결정 #279]`(REQ ID·초안 위치·승격 경로). 이 문서는 **공통 템플릿·작성 규칙**(ARCH-A, 2026-11-11)과 **색인**(PM-3 몫, 아래 §6 자리)을 담는다.
> 근거: [requirements-audit.md](requirements-audit.md) §3(명세 공백) · §9(임시 템플릿 — 이 문서가 대체한다). 밸런스 실험 단위·판정 절차는 [balance-spec.md](balance-spec.md)(PM-2), 후반 경험 게이트는 [late-game-gate.md](late-game-gate.md)(ARCH-E)

## 1. 왜 템플릿인가

규칙은 결정(#n)으로 하나씩 들어왔다. 결정마다 "무엇을 바꾸나"는 있지만 "플레이어의 선택 → 기회비용 → 상태 변화 → 결과 → 성공 기준"의 고리는 흩어져 있다(audit §3). 그래서 같은 질문이 매번 다시 나온다 — 이 규칙이 무엇을 지키나, 어디서 깨지나, 무엇으로 합격을 판정하나. 템플릿은 그 고리를 한 칸에 모으는 형식이다. **새 규칙을 만들지 않는다** — 기존 결정과 코드를 가리키고, 비어 있는 칸을 드러낸다.

## 2. 템플릿 `[제안 P-ARCH-39]`

```
### REQ-<파트>-<n> <이름>
상태: 초안 | 제안 | 확정 | 구현 | 검증 | 폐기      담당: <파트>     의존: REQ-…, #…

1. 핵심 재미와의 관계      — mvp.md 핵심 재미 ①~⑥ 중 어느 것을 지키나/만드나. 한 줄
2. 선택과 기회비용         — 플레이어가 고르는 것(A)과 그 대가(B를 포기). 선택이 없으면 "선택 없음(자동·규칙)"이라고 쓴다
3. 입력·전제               — 읽는 상태 필드·콘텐츠 값·시나리오 조건. 잠금(시나리오·테크 게이트)
4. 상태 전이               — 틱 단계(step.ts 0~9) 또는 행동 이름 · 바뀌는 필드 · 같은 단계 안의 순서 의존
5. 수식                    — 식 그대로(코드 함수 이름과 함께). 손잡이는 `[튜닝]` 표시
6. 단위·반올림             — 원(정수)·L·LPA·ABV(0~1)·품질(0~100)·개월. 언제 반올림하나(저장 전/표시만), 반올림 방식(§4)
7. 보이는 정보             — 플레이어가 보는 값: 참값 / 추정값(±σ) / 결과 공개(행동 뒤) 구분. 정보 계약(architecture.md §11)에 맞는가
8. 불변식                  — 항상 참이어야 하는 것(테스트로 쓸 수 있게 — "현금은 정수", "보호 통은 자동 기능이 쓰지 않는다")
9. 정상 사례               — 대표 시나리오 1~2개와 기대 결과(숫자)
10. 엣지 케이스             — 최소 3개. 경계값·빈 목록·동시 발생·옛 세이브·판 끝(180개월) 등
11. 악용                    — 최소 1개(없으면 "찾지 못함 — 이유"). 무한 반복·차익·정보 역산·자동화 우회
12. 측정 지표               — balance-spec 공통 지표 이름 그대로(새 지표면 정의를 함께)
13. 테스트                  — 단위 테스트 / 봇 실험(스크립트·환경 변수) / 세이브 재생 / 사람 판 — 각각 무엇을 보나
14. 합격 기준               — 기존 결정·오너 결정만 인용. 근거가 없으면 "오너 결정 대기"(임계값을 지어내지 않는다)
15. 결정·코드 연결          — #n · 파일·함수 · PRD 절
```

필수 칸: 1·2·4·5·7·8·10·13·14·15. 나머지는 해당 없으면 "해당 없음 — 이유" 한 줄. 사실·추론·가설은 audit 표기(**[사실]·[추론]·[가설]**)를 그대로 쓴다.

## 3. 상태의 뜻

| 상태 | 뜻 | 들어가는 조건 |
|---|---|---|
| 초안 | 파트가 쓰는 중 | — |
| 제안 | 칸이 다 찼고 `[제안 P-…]`로 오너 결정을 기다린다 | 필수 칸, 엣지 3개, 합격 기준(또는 "오너 결정 대기") |
| 확정 | 오너가 결정(#n 발급) | PM 번호 발급 |
| 구현 | 코드가 들어갔다 | PR 머지 + 13의 단위 테스트 |
| 검증 | 14의 합격 기준을 13의 방법으로 확인했다 | 실험 기록(커밋·시드·봇 버전 — balance-spec) |
| 폐기 | 대체되거나 철회 | 대체 REQ·결정 번호 |

- 확정 뒤 수식·합격 기준을 바꾸면 **새 결정**이 필요하다(결정은 오너만). 표현만 고치는 것은 상태를 바꾸지 않는다
- Phase D에 "확정·구현·검증" REQ를 PRD 해당 절로 승격한다(#279) — 승격 뒤 PRD가 정본, REQ 칸은 PRD 절을 가리킨다

## 4. 작성 규칙

1. **ID:** `REQ-<파트>-<n>`(#279). 파트 = PROD·MKT·MGT·META·ARCH. n은 파트 안에서 1부터, 다시 쓰지 않는다. 임시 결정 ID(`P-…`)·단계 T 확인 항목(`T-…`)과 따로 센다
2. **위치:** 파트 초안은 `<파트>-stage-t.md` 「요구사항」 절(#279). ARCH는 이 문서 §5와 architecture.md 해당 절
3. **한 REQ = 한 규칙.** 두 결정을 묶으면 엣지·합격 기준이 섞인다. 같은 가치를 두 곳에서 다루면(예: 숙성 가치 — PROD `agePerception`·MKT 매력도, audit §6) **한 REQ에서 둘 다** 가리키고 담당을 하나로 정한다
4. **합격 기준은 인용만.** PROCESS §2(60%)·#264·#263·#277·#278과 오너 결정. 새 수치가 필요하면 `[제안]`으로 오너에게 — REQ 안에서 정하지 않는다
5. **수식은 코드와 같은 이름으로.** 함수가 바뀌면 REQ의 5·15칸을 같은 PR에서 고친다(CLAUDE.md "규칙을 바꾸면 해당 문서를 같은 PR에서")
6. **반올림 방식:** 금액은 원 단위 정수, `Math.round`(0.5는 +∞ 쪽 — C# 기본 은행가 반올림과 다르다, architecture.md §9.4). 표시 반올림과 저장 반올림을 구분해 쓴다
7. **보이는 정보** 칸은 architecture.md §11 정보 계약의 등급(참값 금지 / 추정 / 결과 공개 / 합계)으로 적는다
8. **적용 순서:** 핵심 경제·생산 규칙과 **바꿀 대상**부터 — #117 숙성 프리미엄(PROD-A) · #154 SKU CES(MKT-A) · #200 자동 가격(MKT-B) · #252·#260 보호 · #263·#264 판정 · #167 순자산 참 품질(ARCH-C). 이미 안정된 규칙은 바꿀 때 쓴다

### REQ-ARCH-1 플래그십 예비 통 보호
상태: 구현(ciosryu/distillery#288 — 머지 대기)      담당: ARCH(태그·화면) · PROD(자동 납품 거르기, #249 ②)     의존: #252·#260·#261

1. 핵심 재미 — ③ 시간의 복리·헤리티지: 오래 둔 통이 판 끝 플래그십이 된다
2. 선택과 기회비용 — 가장 오래된 후보 n통을 예비로 묶으면 그 통을 지금 팔아 얻을 현금(봇 P7 기준 순자산 −0.5억, 약 5%)을 포기한다. 떼면 자동 기능이 쓸 수 있다
3. 입력 — 시나리오 판, `flagship_sold` 마일스톤 없음, 후보 = `isFlagshipCandidate`(오크 + 남은 달 ≥ 144)·나무 통·고객 소유 아님·오염 확인 아님
4. 상태 전이 — 상태에 저장하지 않는다(`tags.ts reserveCaskIds` 매번 계산). 행동 `tagCasks`가 `SpiritLot.tagIds`·`inventory.reserveOptOut`을 바꾼다. 틱 5단계 자동 납품이 보호 통을 거른다(PROD 연결 뒤)
5. 수식 — 예비 = 직접 붙인 통 ∪ (오크 긴 순 → id 순으로 남은 자리 `PROD_TUNING.flagshipReserve`(4 `[튜닝]`) − 직접 붙인 수, 뗀 원액 제외)
6. 단위 — 통 수(정수)
7. 보이는 정보 — 예비 칩·KPI "예비 k통"(참값이지만 오크 개월·후보 조건은 원래 보이는 값이라 새는 것 없음)
8. 불변식 — ① 손대지 않으면 예비 = #252 집합 ② 보호 통은 자동 납품·자동 통입·맡기기 후보·IB 대상이 쓰지 않는다 ③ 플래그십 판매 뒤·샌드박스에는 예비가 없다 ④ 태그 행동은 현금·원액을 바꾸지 않는다
9. 정상 — 96개월째 후보 6통(70·66·64·62·61·40개월 중 60↑) → 예비 70·66·64·62

## 7. 템플릿 자체의 엣지 케이스

1. **선택이 없는 규칙**(예: 파산 3개월 규칙) — 2칸에 "선택 없음 — 플레이어는 대출·판매로 피한다"처럼 **우회 선택**을 적는다. 비워 두면 기회비용 분석이 빠진다
2. **두 파트가 같은 값을 다룬다**(숙성 가치: PROD `agePerception`·MKT 매력도) — 한 REQ, 담당 하나, 다른 파트는 의존에. 둘로 쓰면 한쪽만 고쳐 이중 보정이 된다(audit §6)
3. **합격 기준이 아직 없다**(#264 범위는 잠정) — "오너 결정 대기 — 후보: …"로 쓰고 상태를 "제안"에 둔다. 근거 없는 수치를 적어 "확정"으로 올리지 않는다
4. **수치만 바뀌는 튜닝** — 단계 T의 손잡이 변경은 REQ 상태를 바꾸지 않는다(5칸의 `[튜닝]` 값만). 식 모양이 바뀌면 새 결정(#276 — T 진입 전 건별 승인)
5. **옛 세이브** — 4칸에 선택 필드가 없을 때의 기본 동작을 반드시 쓴다(#187 — 버전 올림 없음)
