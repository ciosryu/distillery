## 0. 요약

1. **가장 큰 리스크는 성능이 아니라 플랫폼 전제다.** 이번 요청은 "웹(React)이 최종 제품"을 전제로 하지만, PRD는 **Godot 4 + C#, PC(Steam)이 최종이고 웹은 설계 실험실**이라고 결정해 두었다(#34·#35·#40, §13.1). 어느 쪽이냐에 따라 픽셀 뷰·IndexedDB·Web Worker에 투자할지가 갈린다 → §7 질문 1
2. **"캐스크 수천 개" 전제는 현재 설계에서 실측되지 않는다.** 10년(120개월) 봇 플레이에서 원액 든 캐스크는 **126~292개**, 세이브는 **약 0.37~0.60M자**, 상태 전체 복제는 **약 3~4ms**다. 지금 규모에서 Zustand 메모리·리렌더는 병목이 아니다
3. 그래도 규모가 커질 때(20년 시나리오 #2, 해외 증류소 인수 §3.4) 터질 지점과, **규모와 무관하게 지금 있는 정합성 결함**을 실측·코드로 찾았다 — 자리 배정 O(n²), 틱마다 전체 복제, 조용한 세이브 실패, 세이브 마이그레이션 부재, 제품 레코드 무한 증가 (§2.3)
4. **역제시:** 도메인별 Store 분리와 IndexedDB 라이브 DB는 **반대**한다. 대신 **"상태 하나 · 틱 하나 · 경계 하나"** — 단일 권위 상태(내부는 도메인 슬라이스) + 틱 컨텍스트 기반 파이프라인 + 엔진 계약(GameEngine) — 를 세우고, 성능 장치는 **측정 트리거**로 단계 도입한다 (§3, §5)
5. 이 중 엔진 계약·틱 컨텍스트·스키마 정리는 **웹이 최종이든 Godot가 최종이든 버려지지 않는 투자**다. 웹 전용 투자(IndexedDB 세이브 슬롯·픽셀 캔버스·Worker)는 질문 1의 답에 따라 정한다

### 2.3 해석

**지금 규모(10년·단일 증류소)** — 월 처리 10ms 안팎, 세이브 0.6M자 미만. 성능 최적화는 지금 필요 없다.

**규모가 커질 때 터지는 지점** (1,000~10,000개 구간)

| # | 지점 | 위치 | 증상 |
|---|---|---|---|
| P1 | 자리 배정 O(n²) | `ops.ts` `assignSlot` → `slotOccupancy`가 캐스크마다 전체 캐스크를 다시 센다 | 5,000개 0.6초, 10,000개 2.7초 (대량 통입·숙성고 증설 시) |
| P2 | 틱·행동마다 상태 전체 복제 | `step.ts`·`actions.ts`의 `clone(prev)` | 5,000개에서 월 처리의 약 35~40%. 가격 하나 바꿔도 전체 복제 + 전체 직렬화 저장 |
| P3 | 세이브 한도 | `store/game.ts` localStorage | 캐스크 1개 약 720자 → **약 6,500개 전후**에서 한도(브라우저마다 다르고 대체로 오리진당 5MB 안팎 `[확인 필요]`) 초과 |
| P4 | 캐스크마다 기후 재계산 | `ops.ts` `slotClimate` → 캐스크마다 `warehousesOf()` 배열 생성 + `siteOf()` | 숙성고 × 단 수십 칸이면 될 계산을 캐스크 수만큼 반복 |

**규모와 무관하게 지금 있는 결함**

| # | 결함 | 위치 | 결과 |
|---|---|---|---|
| D1 | 저장 실패를 삼킨다 | `store/game.ts` `save()`의 빈 `catch` | 한도 초과·시크릿 모드에서 **진행이 조용히 사라진다** |
| D2 | 버전 간 마이그레이션 없음 | `load()`는 v5 안에서만 `normalizeState`로 빠진 필드를 채우고, `version !== 5`면 버림 | 스키마 버전을 올리는 순간 **모든 세이브가 사라진다** (PRD §13.2는 마이그레이션 함수를 요구) |
| D3 | 제품 레코드 무한 증가 | `blending.ts`가 병입마다 `products.push`, 지우는 곳 없음 | 10년 세이브의 최대 덩어리. `runSales`가 매달 품절 제품까지 순회 |
| D4 | 전 패널이 상태 전체 구독 | `ui/panels/*` `useGame((g) => g.state)` | 아무 행동이나 하면 활성 패널 전체가 다시 그려진다 (지금은 싸지만, 표가 수천 행이면 비싸다) |

## 3. 역제시 아키텍처

### 3.1 원칙 — 상태 하나 · 틱 하나 · 경계 하나

1. **권위 상태는 하나**(`GameState`). 세이브·리플레이·골든 테스트의 단위가 하나다
2. **시간은 둘:** 시뮬레이션 시간(월 틱, 이산·결정론)과 렌더 시간(`requestAnimationFrame`, 연속·표현 전용)을 섞지 않는다. 걷는 직원·증기 같은 애니메이션 상태는 `GameState`에 들어가지 않는다
3. **경계는 하나:** `GameEngine` 계약 — 명령(Command)이 들어가고 스냅샷(읽기 전용)이 나온다. 지금은 같은 스레드, 필요하면 Web Worker, Phase G에서는 C# 라이브러리가 **같은 계약**을 구현한다
4. **성능 장치는 측정 트리거로** 단계 도입한다 (§5). 측정 없이 미리 복잡도를 사지 않는다

### 3.2 레이어

```
content/   데이터 (원재료·설비·캐스크·지역·이벤트·테크 노드) — JSON으로 옮길 수 있는 형태
   ↓
sim/       순수 TypeScript · 결정론 · React 의존 없음
  systems/   production · maturation · contracts · market · ops · finance · hr · events · research
  tick.ts    buildTickContext → 시스템 파이프라인 → MonthReport
  engine.ts  GameEngine 계약: dispatch(cmd) · advance(opts) · snapshot() · subscribe()
   ↓ 스냅샷(읽기 전용)                ↑ 명령
store/     useGame — 읽기 모델 1개 + 도메인 셀렉터(selectors/finance.ts 등)
           useUi   — 탭·선택·토스트·카메라 (비영속)
   ↓
ui/        대시보드 (React 표·차트) — 셀렉터만 쓴다
view/      픽셀 뷰 (canvas 1개 + rAF) — layout(state) → SceneModel
persist/   세이브 저장소 + 마이그레이션 체인
```

```ts
// 엔진 계약 — 지금은 동기 구현, Worker·C#은 같은 모양의 비동기·네이티브 구현
interface GameEngine {
  snapshot(): Readonly<GameState>;
  dispatch(cmd: Command): CommandResult;                 // 플레이어 행동 (지금의 Action)
  advance(opts: { months: number; stopOn?: StopReason[] }): AdvanceResult; // 리포트 목록 + 멈춘 이유
  subscribe(fn: (snap: Readonly<GameState>) => void): () => void;
}
type StopReason = 'pendingEvent' | 'cashWarning' | 'bankrupt' | 'researchDone' | 'equipmentReady';
```

### 3.3 Store — 도메인별 Store 분리에 대한 반론과 대안

**반론 (도메인별 Zustand store 4개 안):**
- 월 틱은 **도메인을 가로지르는 하나의 트랜잭션**이다. 생산 원가 → 현금, 판매 → 주세 → 현금, 숙성 → 보관비·보험료, 직원 스탯 → 생산 한도·증발량. Store를 나누면 한 틱에 `set()`이 여러 번 일어나 **중간 상태가 렌더되거나**(현금은 빠졌는데 재고는 그대로), 이를 막는 배치 장치를 따로 만들어야 한다
- 세이브·로드·리플레이·**Godot 이식 골든 테스트**(§13.1)가 Store 수만큼 쪼개진다. 결정론 검증은 상태가 하나일 때 가장 쉽다
- 도메인 간 읽기(재무가 캐스크 가치로 보험료를 계산)가 Store 간 의존으로 바뀐다

**대안 — Store는 하나, 상태 안을 도메인 슬라이스로:**

```ts
interface GameState {
  meta;        // 버전·시드·월·지역·입지·이름·상태·nextId (+ v8: scenario — 시나리오 잠금 키·경제 값·목표, skeleton S-8)
  world;       // 날씨·원재료 시세·트렌드·벌크 지수·보정치
  finance;     // 현금·대출·투자·마케팅 예산·연속 적자 월
  hr;          // 직원·후보·하우스 스타일
  production;  // 설비·레시피·생산 지시
  inventory;   // 탱크 원액·캐스크·캐스크 주문·숙성고
  commerce;    // 제품·제품 아카이브·인지도·관광·전통주 출고량
  b2b;         // 계약·제안·신뢰도·브로커·캐스크 입찰
  research;    // 테크 완료·진행 중 연구 (신규)
  events;      // 대기 이벤트·예보·로그·쿨다운
  history;     // 월 리포트(최근)·연 요약
}
```

- UI는 원시 상태에 접근하지 않고 `store/selectors/<도메인>.ts`만 쓴다 → 화면 코드가 상태 모양 변경에서 격리된다
- **실제로 분리할 가치가 있는 경계는 "영속 vs 비영속" 하나뿐**이다 → `useUi`를 따로 둔다
- **솔직한 한계:** 월 틱에서는 거의 모든 슬라이스가 바뀐다(직원 XP, 제품 판매 지수, 현금, 캐스크…). 그래서 슬라이스 분리의 **리렌더 이득은 턴 사이의 행동**(가격 변경·채용 등)에서만 나온다. 턴당 한 번의 리렌더는 원래 싸다. 슬라이스의 주된 가치는 **코드 조직·이식(C# 클래스 대응)·향후 부분 복사(§5 단계 D)** 다

### 3.4 캐스크 핫패스

| 장치 | 내용 | 해결 |
|---|---|---|
| 틱 컨텍스트 | 틱 시작에 한 번: 캘린더, 날씨 표본, **숙성고 기후표[숙성고 × 단]**, 직원 역할별 최고 스탯, 보정치 조회 맵, 유효 원재료 가격. 캐스크는 표를 **조회만** 한다 | P4 |
| 슬롯 점유 인덱스 | `Map<"숙성고:단", 개수>`를 틱·행동마다 한 번 만들어 자리 배정을 O(1)로 | P1 |
| 원액은 캐스크가 품는다 | 지금처럼 `Cask.contents`에 원액을 둔다(1:1, 원액은 공유되지 않음). 별도 원액 테이블 + id 참조로 정규화하면 조인만 늘고 이득이 없다 | — |
| 배치 id | 원액에 `batchId`(같은 배치·같은 달 통입 묶음)를 추가. UI는 **코호트 단위**로 보여 준다("2027-03 몰트 · 버번 배럴 × 24"). 수천 행 표 대신 묶음 → 필요할 때만 펼침 | D4 |
| 예비: 코호트 숙성 | 같은 배치·같은 캐스크 상태·같은 칸 기후의 캐스크는 숙성 결과가 같다(누수·오염만 개별). 5,000개를 넘으면 묶음 단위로 계산 | 트리거 F |

### 3.5 틱 처리 시점

**두 개의 시계**

| | 시뮬레이션 틱 | 렌더 프레임 |
|---|---|---|
| 주기 | 플레이어가 진행할 때 1개월씩 | 초당 약 60회 |
| 성격 | 이산·결정론·순수 함수 | 연속·표현 전용·버려도 되는 상태 |
| 난수 | `rngFor(seed, month, stream)`만 | `Math.random` 허용(표현용) |
| 상태 | `GameState` | `view/` 내부 (애니메이션 위상·카메라) |

**틱 파이프라인** (Step 3에서 확정)

```
0 컨텍스트   캘린더 · 날씨 표본 · 숙성고 기후표 · 직원 집계 · 보정치 맵 · 유효 원가
1 이벤트     예보 → 발생 → 보정치·날씨 충격 등록 (이번 달부터 적용)
2 생산       발효실 온도 → 발효 기간 → 증류 → 탱크 원액
3 숙성       캐스크마다 기후표 조회 → 증발(엔젤스 셰어)·도수·향미 → 누수·오염
4 계약 납품  B2B 계약 이행·위약금
5 판매       수요 → 소매 역량 → 매출 → 주세
6 운영       관광 · 캐스크 오너십 인도 · 사무직 · 직원 생애주기(에이징 커브·은퇴)
7 재무       급여 · 관리비 · 유지비 · 보관비·보험료 · 대출
8 성장       XP · 연구 진척 · 후보·브로커·계약 제안 갱신 · 시세 랜덤 워크
9 판정       지급 능력(3개월 연속 적자 → 파산) · 리포트 · 자동 진행 멈춤 사유
```

- PRD §2.2는 이벤트를 6번째에 두지만 코드는 맨 앞이다. **코드 순서가 맞다고 본다** — 이번 달 폭염·한파가 이번 달 숙성·생산에 반영돼야 인과가 보인다. PRD §2.2를 코드에 맞춰 고치길 제안한다

**날씨 난수 (신규 제안)** `[제안]`

- 월 기온·습도 이상치를 AR(1)로: `a(t) = ρ·a(t−1) + σ·√(1−ρ²)·ε`, `ε ~ N(0,1)`, 스트림 `rngFor(seed, month, 'weather')`. 기온 σ ≈ 1.2°C, 습도 σ ≈ 4%p, ρ ≈ 0.6 `[튜닝]`
- 이상치를 상태(`world.weather`)에 저장 → 리포트·예보·화면에 보이고, 다음 달이 이전 달에 이어진다("더운 여름이 계속된다")
- **이벤트는 결과가 아니라 입력을 바꾼다:** 폭염은 지금 "증발 ×1.7"이지만 → "기온 이상치 +4°C, 2개월"로. 그러면 증발·추출 속도·발효 기간·도수 변화가 **한 원인에서 일관되게** 따라온다 (PRD #18 "확률은 정보에"와 같은 결의 원칙)
- **리스크:** 증발 계수가 `exp(0.13·ΔT)`라서 평균 0인 난수라도 기대 증발이 오른다(젠센 부등식). σ = 1.2°C면 `exp(0.13² × 1.2² / 2)` ≈ **+1.2%**, σ = 1.5°C면 **+1.9%**. 시드 간 분산도 커진다 → v1.4 밸런스 재실행 필요

**자동 진행** — "N개월 진행·다음 이벤트까지 진행"(PRD §2.1)은 한 달마다 제어권을 돌려주는 청크 루프로 만든다. 선택 이벤트·현금 경고에서 멈추고, 진행 막대를 보여 주며, 취소할 수 있다

### 3.6 영속화 — IndexedDB는 "세이브 저장소"로만

**반론 (캐스크를 IndexedDB에 두고 매 틱 조회·갱신하는 라이브 DB 안):**
1. 틱이 비동기 I/O가 되어 순수 함수·결정론이 깨지고 골든 테스트가 어려워진다
2. 1만 개도 JSON 7M자 — 메모리에 넉넉히 들어간다. 메모리 연산보다 느릴 뿐이다
3. Godot 이식에 대응물이 없다

**채택:**
- **세이브 슬롯 저장소**로 IndexedDB — localStorage 5MB 안팎 한도가 없고(쿼터는 브라우저·디스크에 따름), 문자열 직렬화 없이 저장하며, Web Worker에서도 쓸 수 있고(localStorage는 Worker에서 못 쓴다), 비동기라 저장 중 화면이 멈추지 않는다
- **마이그레이션 체인:** `migrations: Record<number, (s) => s>` — 로드할 때 v5 → v6 → … 순서로 올린다. 버리지 않는다. 지금의 `normalizeState`(v5 안의 빠진 필드 채우기)는 체인의 첫 단계로 흡수한다 (D2)
- **저장 시점:** 행동마다가 아니라 턴 종료 후 + 디바운스. **실패는 토스트로 알린다** (D1)

### 3.7 데이터 수명 관리

- **제품:** 재고 0이고 12개월 판매가 없으면 `productArchive`(이름·카테고리·출시월·누적 판매)로 압축하고 향미 객체는 버린다 (D3)
- **리포트:** 최근 24개월은 상세, 그 이전은 연 요약. 10년 차트는 연 요약을 쓴다
- **이벤트 로그:** 이미 60건 상한

### 3.8 픽셀 뷰 레이어 — 웹이 최종일 때만 본격 구현

- **canvas 1개 + `requestAnimationFrame`.** 타일마다 DOM 노드를 만들지 않는다
- `view/layout.ts` — 순수 함수 `layout(state) → SceneModel { tiles: { x, y, kind, ref }[] }`. 설비·숙성고(단별 랙)·직원 자리를 32×32 더미 타일로. **테스트 가능하고, 이후 Codex 작업(스프라이트·애니메이션)의 계약**이 된다
- 갱신: `useGame.subscribe`(비반응형 구독)로 스냅샷이 바뀔 때만 SceneModel을 다시 만든다. React 리렌더를 거치지 않는다
- 클릭 → `useUi.select(ref)` → 대시보드 패널이 상세를 보여 준다
- Godot가 최종이면 이 레이어는 버려지는 투자다 → 그때는 만들지 않거나 디버그용 최소판만

### 3.9 테크트리 게이트

- 모든 잠금 판정은 `isUnlocked(state, key)` 하나로 (PRD §14 Phase 1 각주, tech-tree §7)
- 노드 정의는 `content` 데이터, 진척은 `research` 슬라이스, 해금된 공정의 향미 효과는 공정 효과 데이터에 둔다(tech-tree §1.1 구현 원칙). 스키마는 Step 2에서 확정

## 6. 리스크·반론

- **슬라이스 재편은 대수술이다.** 많이 쓰는 9개 필드만 약 440곳(캐스크 117 · 현금 102 · 원액 44 · 직원 42 · 리포트 37 …)이고, 전체 상태 필드 접근은 1,000곳이 넘는다(추정). 게임 동작은 바뀌면 안 되므로 재편 전후 `npm run balance -- 20 120 all <KR|JP|TW>` 결과가 같아야 한다(골든 기준). 이득이 주로 조직적(이식·코드 탐색)이므로 **평면 유지 + 셀렉터 모듈만** 하는 B안도 합리적이다 → §7 질문 2
- **날씨 난수**는 PRD #37(일관된 한 전략으로 이길 수 없게)에 맞지만, 증발 기대값 +1~2%와 시드 분산 확대로 v1.4 밸런스 기준선이 흔들린다
- **웹이 최종이 아니면** §3.6 IndexedDB·§3.8 픽셀 뷰·단계 C·E는 버려지는 투자다. 반대로 엔진 계약·틱 컨텍스트·스키마 정리는 Godot 이식에도 그대로 쓰인다
- **측정은 Node 22(V8)다.** 브라우저·저사양 기기에서는 더 느릴 수 있다(추정). 트리거 판정은 브라우저에서 잰 값으로 해야 한다

| F 코호트 숙성 | 5,000개 초과 | 2,500개 | 범위 밖 |

**함의:** 30년·2,500개를 웹에서 돌리려면 C·D·E 세 장치가 모두 필요하다. 이 중 C·E는 웹 전용 투자다 → **질문 1(플랫폼) 답이 다음 단계의 범위를 정한다.** Godot가 최종이면 C·E 대신 C# 이식(Phase G)에서 같은 엔진 계약을 구현하면 된다.

### 9.3 발견한 구조 문제 — 이벤트 섞기

이벤트 엔진은 매달 `[...EVENTS].sort(() => rng.next() - 0.5)`로 목록 전체를 섞어 판정한다. 그래서 **이벤트를 하나만 추가해도 모든 시드의 이벤트 순서가 바뀐다**(블렌딩 의뢰를 이벤트로 넣었다가 시드 1의 1월에 한파가 새로 생겨 생산이 멈췄다). 또 비교 함수 기반 섞기는 균등하지 않다.
- 이번에는 블렌딩 의뢰를 독립 난수 스트림의 월간 제안으로 바꿔 피했다
- **권장:** 이벤트마다 `rngFor(seed, month, 'event:' + id)`로 따로 굴리면 콘텐츠를 더해도 기존 이벤트 결과가 그대로다. 밸런스가 한 번 바뀌므로 Godot 이식 전에 하는 것이 맞다 `[제안]`
