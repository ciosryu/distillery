# Claude Code 단계별 작업 프롬프트

이 파일과 `README.md`, `decision-trace.md`, `decision-trace.json`, `evidence/`를 같은 패키지로 제공한다. 아래 단계는 순차 실행한다. 현재 작업 사본에 사용자 변경이 있으면 먼저 보존하고, 확인한 최신 `main`에서 작은 작업 브랜치를 사용한다. 정본은 GitHub 기본 브랜치가 아니라 저장소 문서가 지정한 `main`이다.

최신 목표 검토: 기존 확정안은 15년 싱글 몰트 위스키의 최초 유상 판매다. 사용자는 이후 12년 싱글 몰트 위스키 출하안을 질문했고, 감사 권장은 12년 최초 유상 출하다. **질문을 확정 지시로 오기하지 않는다.** 목표 연수와 출하/판매 사건을 RuleSet으로 분리하고, 최종 채택된 요구를 확인할 수 있을 때 그 규칙으로 코드·테스트를 고정한다. 자료가 없으면 독립된 조사·문서·기반 계약 작업을 계속한다.

## 공통 지시문 — 매 단계 앞에 붙이기

```text
ciosryu/distillery 프로젝트의 확정 설계를 구현한다. 먼저 CLAUDE.md, docs/README.md, PROCESS.md, STATUS.md, 해당 파트 설계 문서를 읽는다. 정본은 main이며 claude/dazzling-mccarthy-40er1r는 동결 브랜치다. 감사 기준은 main 45a138f6e7eae64453e63646c1429025992386a9, 기존 비교 기준은 d0b6886506b3f8da50bf37aa2ad11bbb84e733fe다. 새 main이 있으면 그 이후 변경을 별도 표로 조사하고 이번 감사 결론을 무조건 덮어쓰지 않는다.

첨부 감사 패키지의 최신 사용자 요구와 확인한 오너 확정을 우선한다. LEGACY-001~270, CORE-001~109, REPO-271~307은 별도 식별자다. 원장의 #번호를 재발급하지 말고 저장소 규칙에 맞는 임시 ID를 쓴다. CORE 80개는 원문 미확보 상태다. 추정 구현·전수 감사 완료 표기·기능 이관을 의미하는 DEFER로의 임의 분류를 하지 않는다.

게임 방향성에 관한 선택 질문을 새로 만들지 않는다. 사소한 구현 방식은 기존 패턴과 최소 변경을 기준으로 정하고 근거를 기록한다. 확정 근거가 없는 기능은 EVIDENCE_PENDING으로 남기고 독립된 확정 기능 작업을 계속한다. 12년 목표의 최신 질문은 검토안이고 기존 15년 확정을 덮어쓴 지시로 기록하지 않는다. 실제 후속 확정이 있으면 그 요구를 우선한다.

문서 작성, 구현, 실행한 검증, 밸런스 합격을 구분한다. 한 PR은 한 주제로 제한하고 코어·파트 소유 경계를 따른다. 무관한 재작성·튜닝·Godot 이식을 섞지 않는다. 허가되지 않은 원격 머지·메시지 전송은 하지 않는다. 결과에는 변경 파일, 요구사항 ID, 검증 결과, 미검증·남은 위험을 적는다.
```

## 단계 2A — 계보·병입·판매 기반의 최소 패치

```text
동결한 계약만 구현하라. 기존 GameState/명령/월 틱 엔진을 유지한다. 배치 출처·기여 LPA·분할/혼합 부모·자가/매입/미상·증류소 자격·적격 목재 숙성 기간을 보존하라. 같은 레시피 탱크 원액의 묵시적 합치기는 명시적 혼합 승인과 출처 기록 없이 일어나지 않게 하라. 단일 batchId나 recipeIds 집합을 완전 계보로 취급하지 마라.

제품 SKU와 병입 로트를 분리하거나 동등한 출고 추적 구조를 추가해 어떤 로트가 실제 팔렸는지 알 수 있게 하라. 출고 거래에는 당시 자격·수량·양의 대가·거래 상태를 기록한다. 과거 totalSold를 현재 보충 재고의 나이와 결합해 승리를 소급 인정하지 마라. 단순 이동·무료·예약 선수금만의 수령은 정상 유상 출고가 아니다.

의미가 바뀌는 상태는 스키마/규칙 버전을 올리고 migrateSave와 fixture를 추가하라. 옛 출처를 만들지 말고 unknown으로 보존하라. 기존 판의 구규칙 재개와 새 규칙 판을 구분하라.

완료: 분할/혼합/통입/피니싱/병입/보충/판매의 LPA·원가 보존, 명시적 손실, 중복 소비 방지, 출처미상 적격 탈락 테스트 통과. typecheck/test/build와 영향 입지 스모크 통과. 신규 데이터가 없어도 옛 세이브 원본은 보존된다. 경제 수치 튜닝·전체 엔진 재작성은 하지 않는다.
```

```text
완료: 동일 관측/서로 다른 참값인 짝 상태에서 UI·추천·추정 평가·자동화 선택 동일, 실제 판매 결과의 차이는 허용. 병입/판매 뒤 참값 공개 경로 0. 국내만으로 전체 캠페인의 경로 존재, 수출·상세 HR 재해금 없음, 기본 인력 역량 유지. 공통 검사·세이브·범위 통합 테스트 통과.
```

## 단계 4 — 밸런스 테스트와 후반 경험

```text
앞 단계 통합 검사가 통과한 고정 SHA와 RuleSet에서만 시작하라. 봇은 플레이어가 알 수 있는 관측만 사용하며 판정은 게임의 정상 판매·승리 함수를 그대로 쓴다. 구순자산 성공률이나 120개월 샌드박스 결과를 새 캠페인 성공률로 인용하지 않는다.

공식 프리셋별·규모별 고정 40시드, 사전 고정 합리 전략군을 실행한다. 목표가 15년이면 우선 240개월(360 민감도), 12년이면 우선 180개월(240 민감도)을 잠정 측정 창으로 삼되 관측 종료는 게임 강제 종료가 아니다. 승리/파산/미완주/관측 종료를 분리한다. 목표 판정과 순자산 성과 순위도 분리한다.

국내 현금흐름·장기 보유·혼합형, SKU 수, 관광/차입 유무, 수동/정책 가격을 비교한다. 장기 보유는 적합한 B/C 정책에서도 평가하고 A 기본값을 계속 쓰는 사람의 경험은 별도 기록한다. 최초 적격 출고월, 최저 현금, 위기/차입, 가치평가 3종, 적격 원액 소모 원인, 병입 창, 관측의 비용/가치, 후반 개입을 기록한다.
```

## 단계 5 — Godot 이식 및 EA 출시 판정

```text
TypeScript 기준 규칙과 콘텐츠가 고정되고 통합/밸런스/후반 경험 관문을 통과한 뒤에만 C# 이식을 시작한다. 엔진 JSON 콘텐츠·명령·상태·난수 스트림·월별 사건의 골든을 먼저 고정한다. 이식과 규칙 재설계를 동시에 하지 않는다.
```
